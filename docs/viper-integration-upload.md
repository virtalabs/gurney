# viper-integration-upload scenario

The `viper-integration-upload` scenario is a focused probe of Viper's
`/api/v1/assets/integrationUpload` endpoint. It runs a minimal Viper stack
(`viper-postgres`, `viper`, and a `replay` runner) and sends several crafted
payloads that are structurally similar to Blueflow's connector output.

## Purpose

- Isolate **business validation rules** in Viper's `assetsIntegrationUpload`
  handler without involving Blueflow, TapirX, or Orthanc.
- Compare how small variations in the payload (location fields, `cpe`/`role`,
  pagination fields, `next`/`previous` values) affect whether Viper accepts or
  rejects the request.

## Topology and facts

- Topology: `topologies/blueflow-local/topology.yaml`
- Scenario file:
  - `topologies/blueflow-local/scenarios/viper-integration-upload/scenario.yaml`
- Key facts:
  - `viper_url`: `http://viper:3000`
  - `viper_integration_upload_url`: `http://viper:3000/api/v1/assets/integrationUpload`
  - `viper_api_key`: taken from `VIPER_API_KEY` env or generated by the
    `create-viper-api-key` command.

## Commands and payload variants

1. **create-viper-api-key**
   - Node: `viper`
   - Runs `npm run db:create-test-api-key` and captures `API_KEY=...` into
     `VIPER_API_KEY` if not already set.

2. **post-baseline-payload**
   - Node: `replay`
   - Sends the **baseline** payload that mirrors the observed Blueflow →
     webhook payload (empty `cpe`/`role`, empty `{}` `location`,
     `pageSize: 10`, `next`/`previous: null`).

3. **post-with-location-fields**
   - Same as baseline, but `location` is populated with
     `facility/building/floor/room`.

4. **post-with-nonempty-cpe-role**
   - Same as baseline, but `cpe` is set to a sample CPE string and `role` to
     `"Imaging Modality"`.

5. **post-with-page-size-1**
   - Aligns pagination fields with the Viper example:
     `pageSize: 1`, `totalCount: 1`, `totalPages: 1`.

6. **post-with-non-null-next-prev**
   - Same as baseline, but `next` and `previous` are empty strings instead of
     `null`.

7. **post-all-fields-populated**
   - Combines all of the above:
     - Non-empty `cpe`, `role`, `hostname`, `serialNumber`.
     - Populated `location` object.
     - `networkSegment` and aligned pagination fields.
     - `next`/`previous` as empty strings.

Each command prints a label (for example, `=== baseline ===`) followed by the
response body and an appended `status=HTTP_CODE` line so it is easy to compare
which variants succeed or fail.

## Running the scenario

From the repository root:

```bash
uv run gurney run viper-integration-upload
```

Notes:

- Ensure Viper images are built/pulled and `VIPER_API_KEY` is either set in the
  environment or allowed to be generated by `create-viper-api-key`.
- Inspect the scenario output to see status codes and responses for each
  payload variant; use this to infer which fields Viper treats as required or
  constrained beyond the OpenAPI schema.
